## 🩸 01. THE PROJECT

**Bloodmoon: Sylas** is a single-player browser action game developed as part of my B.Tech 4-1 semester examination project.

Set inside a gothic fortress beneath a blood-red moon, the game allows players to choose a hero, enter a campaign, fight demons and face different bosses.

I wanted to explore how multiple technologies could come together to create an interactive 3D game rather than simply build another basic academic application.

This project became an opportunity to experiment with game development, application architecture, frontend technologies, backend integration and real-time rendering.

> *An idea becomes interesting when you start building it. It becomes a learning experience when you keep improving it.*

### Main Features

- 🧙 Four selectable heroes.
- 🩸 Single-player campaign.
- 👹 50 named level and boss records.
- ⚔️ Normal and heavy attacks.
- 🔥 Magic and special abilities.
- 🛡️ Guarding, dodging and movement.
- ❤️ Health and stamina systems.
- 🗺️ Radar and combat HUD.
- 💎 Souls, rewards, shrines and chests.
- 🏗️ Play, Builder and Hybrid workspace modes.
- 🎮 Keyboard and on-screen controls.
- ⚙️ Camera, language, audio and gameplay settings.
- 🔐 Optional sign-in, registration and guest entry.

**A note about the boss system:** The project contains 50 named boss records and signature-move descriptions. The runtime uses a smaller collection of reusable attack patterns with variations, rather than 50 completely separate combat systems.

## 🧠 03. HOW I APPROACH DEVELOPMENT

I developed this project using an AI-assisted and iterative workflow, often called **vibe coding**.

My approach was to start with an idea, explore how it could be implemented, use AI tools to help with coding, run the application, test the results and improve what needed more work.

I didn't consider generated code a finished solution. I reviewed the implementation, played the game, checked how features behaved and worked through problems when something did not go as expected.

For me, AI is a tool that can support development and learning. Understanding the code, checking the results and taking responsibility for the final implementation are still important.

I believe that building something is only one part of development. Understanding it, testing it and improving it are equally important.

## 🏗️ 05. UNDER THE HOOD

The final application uses an Angular-led hybrid architecture.

Angular acts as the main application host, while the existing React game and builder remain embedded components.

I kept the React runtime because it already handles the real-time game loop, combat and rendering logic. Keeping that system avoids an unnecessary rewrite of the existing game engine.

### Technology Stack

| Technology | Role |
|---|---|
| Angular | Main application host |
| React | Embedded game and builder |
| TypeScript | Application logic and types |
| Three.js | 3D environment |
| WebGL | Browser graphics rendering |
| Node.js | Backend runtime |
| Express.js | Server API |
| MongoDB | Optional database |
| Vite | Development and production build |
| HTML / CSS | Interface and styling |

### Architecture Flow

```mermaid
flowchart TD
    P[Player] --> A[Angular Application Host]
    A --> R[React Game Runtime]
    A --> B[React Builder]
    R --> T[Three.js and WebGL]
    B --> R
    A --> API[Node.js and Express API]
    API --> M[(MongoDB Optional)]
    API --> J[(Local JSON Storage)]
    A --> LS[(Browser Local Storage)]
```

The game and builder share arena and combat settings. Campaign choices and preferences are stored in the browser.

The server provides account-related API routes, but full account-based game progress synchronisation is not implemented.

**Architecture note:** The course subject introduced MEAN Stack Web Technologies. The final project uses Angular as its main host while retaining React for the game and builder. It is therefore a hybrid implementation, not a pure MEAN Stack application.

## 🔧 06. GAME SESSION IMPROVEMENTS

The final build includes improvements to campaign navigation and game-session handling:

- Fresh installations start from the Cover screen.
- New players begin at Level 1.
- Selecting a level starts a clean session.
- Retry and replay create fresh sessions.
- Next Level starts a new session.
- Pause → Restart resets the current level.
- CAMP navigation returns to the Dashboard or Cover.
- Level backgrounds use their configured settings.
- Enemy types match the implemented spawn branches.
- Level reward souls are not counted twice.

These changes help make navigation and gameplay progression more consistent.

## 🚀 07. GETTING STARTED

### Requirements

- Node.js 20.19 or newer in the 20.x series, or 22.12 or newer.
- npm.

### Installation

**1. Clone the repository**

```bash
git clone https://github.com/kaithepallivijayvardhan08-spec/Bloodmoon-Sylas-game-for-final-presentation.git
```

**2. Open the project directory**

```bash
cd Bloodmoon-Sylas-game-for-final-presentation
```

**3. Install dependencies**

```bash
npm install
```

**4. Start the development server**

```bash
npm run dev
```

**5. Open the local address**

```text
http://localhost:3000
```

The terminal prints the local development address.

### Production Build

```bash
npm run build
```

### TypeScript Check

```bash
npm run lint
```

### Automated Tests

```bash
npm test
```

The current automated tests cover the Academy curriculum and progress functionality. The game runtime does not yet have a dedicated automated gameplay test suite.

## 🗄️ 11. OPTIONAL DATABASE CONFIGURATION

MongoDB is optional for local play.

To configure it:

1. Copy `.env.example` to `.env`.
2. Set `MONGODB_URI`.
3. Set `MONGODB_DB` if needed.
4. Keep your credentials private.

Without a working MongoDB connection, the server uses:

```text
data/game_db.json
```

Never commit your real `.env` credentials to GitHub.

## 🔮 12. LIMITATIONS & FUTURE PLANS

This is a learning prototype, not a production-hosted game.

Some areas still need more work:

- More distinct boss behaviours and combat patterns.
- Additional environments and characters.
- Stronger account security and authorisation.
- Better account-based save and progress support.
- More automated gameplay tests.
- Wider browser and device testing.
- Further performance and accessibility improvements.

There are no measured performance or user-study results at this stage. Further development and testing are needed before a public production release.

I prefer being honest about what a project can currently do and what still needs improvement.
